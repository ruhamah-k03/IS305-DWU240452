## OOP Features
- Encapsulation: private fields using `#`.
- Inheritance: StudentRequester, StaffRequester, ServiceOfficer and Technician extend User.
- Request inheritance: ICTSupportRequest, MaintenanceRequest and CleaningRequest extend ServiceRequest.
- Constructor chaining: subclasses use `super()`.
- Overriding: specialised requests override `getRequestSummary()`, `calculatePriorityScore()` and `getTargetResolutionHours()`.
- Polymorphism: all specialised requests can be processed through common method calls.
- Abstraction: ServiceRequest contains abstract-style methods that throw errors unless implemented by a subclass.
- Composition: a ServiceRequest contains a requester User object.

## JSON Persistence
The system stores simulated data only. No database is used.

- `users.json` stores users.
- `serviceRequests.json` stores request data.
- `requestHistory.json` stores the request history entries generated by approved workflow actions.
- `auditLog.json` stores audit actions.

JSON contains data only. It does not contain executable JavaScript, passwords or confidential information.

## Object Restoration
Saved request records contain a `requestType`. `ServiceRequestFactory.createFromData()` uses this value to recreate the correct specialised class after the program starts.

## Workflow
Submitted → Reviewed → Assigned → In Progress → Resolved → Closed

Cancelled is a final status.

## Sample Scenario
1. Register a Student Requester.
2. Submit an ICT Support request.
3. A Service Officer reviews the request.
4. The officer assigns a Technician.
5. The Technician begins work and adds a progress note.
6. The Technician resolves the request.
7. The Service Officer verifies and closes the request.
